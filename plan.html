Implementation Plan · align before build

Irembo Journey Companion

Aligning the Claude Design handoff bundle (gov-services-journies) with our existing project, into one build plan. The design is a direct continuation of our prototype — this plan unifies the two data models, sets the target architecture, and surfaces the decisions to confirm before any production code is written.

Design source: claude.ai/design bundle, 2 chats, citizen app + admin Our base: dataset.json · schema.json · wireframes.html Status: M0 + M1 complete ✓ — citizen app (M2) next

1What the design delivers

The bundle is a high-fidelity HTML/CSS/JS prototype (React 18 + in-browser Babel — prototype-only). Two surfaces, one shared data + engine layer.

🧭 Citizen app new fidelity

The journey assistant, built around a left→right dependency graph (the centerpiece we'd only timelined).

  • 3-screen flow: Goal → Questions → Journey graph
  • Sugiyama-lite DAG layout (layered, crossing-reduced), bezier edges
  • Citizen-friendly nodes: icon · step number · plain "where you do it" · human time · "easy to forget" flag
  • Click node → detail panel; progress tracking (unlock dependents, green flow); filters; pan/zoom
  • 6 journeys fully modeled: business, land, birth, passport, driving, marriage
  • Tweaks: node variant (Cards/Minimal/Transit), density, dark mode, brand color, language toggle

🛠️ Admin console new surface

How service data gets in and stays trustworthy — admin.html, linked from the citizen topbar.

  • Catalog dashboard — every service with status, source, journeys-using, KPIs, search/filter
  • Import from Irembo wizard: Source (URL) → Extract (scrape + parsed fields w/ confidence) → Dependencies (auto-suggested links + new-doc flagging) → Done
  • Service editor — form + live "neighbourhood" graph preview (comes-before → this → unlocks)
  • Lifecycle: Draft → Needs review → Published, with a review queue; localStorage persistence
Key realization: the admin's Draft→Review→Published lifecycle is the governance mechanism for the data-quality problem we'd flagged — every fee/rule marked CONFIRM / sourceConfidence: needs-verification now has a workflow to become verified.

3The alignment thesis

The design and our repo are not two things to merge awkwardly — they are the same system at two maturities. The design literally bundled our wireframes.html and extended its engine. So the alignment is mostly promotion, not reconciliation:

One data model

dataset.json + schema.json become the single source of truth. The design's dataset.js is its richer content; we fold that in and validate against the schema.

One engine

The design's engine.js (Sugiyama layout, critical-path rollup, friendly formatting) supersedes our wireframe engine. Port to TypeScript; keep it pure & framework-free.

Two UIs, shared core

Citizen app and admin console are both thin React clients over the same engine + data. The future side-panel becomes a third client.

5Target architecture

Keep the prototype's clean separation (pure data + pure engine + thin UI), but build it for production. The engine and data are framework-agnostic so the citizen app, admin, and future side-panel all reuse them.

Data layer · /packages/data
dataset.json (6 journeys) + schema.json + migration & validation scripts. The single source of truth, version-controlled, CI-validated.
Engine · /packages/engine (TypeScript)
Port of engine.js: profile/conditions, activeSteps, buildEdges, Sugiyama layout, status, critical-path rollup, warnings, friendly formatters. Pure, tested, no DOM.
Citizen app · /apps/citizen (Next.js + TS)
GoalScreen · QuestionsScreen · GraphCanvas + NodeCard · DetailPanel · JourneyBar · TweaksPanel · icons. Reads engine output. SSR/SEO so each journey is an indexable, shareable URL.
Admin console · /apps/admin (React + TS)
Catalog · ImportWizard (Source/Extract/Dependencies/Done) · ServiceEditor + MiniGraph · ReviewQueue. Writes data via API; same engine for previews.
Backend · /services/api + scraper (new)
Real DB (Postgres), data API, auth/roles, and the server-side Irembo scraper the prototype simulates. Out of scope for Phase 1 demo; in scope for Phase 2.

Stack decision ✓ locked

Next.js + TypeScript. The design is already React; the engine/data port cleanly to TS. Next.js (over plain Vite) gives SSR/SEO — each journey becomes a server-rendered, indexable, shareable URL, which matters for a public-good tool people find by searching "how to open a restaurant in Rwanda." The pure engine + data live as framework-agnostic packages so the admin and future side-panel reuse them. Tokens become CSS variables (already structured that way in styles.css).

8The admin pipeline = data governance

This is where the design solves a strategy problem (Q4: "get the real dependency rules"). The flow, end to end:

Irembo page ──scrape──► raw fields + confidence ──► Extract review (edit) ──►
Dependency linker (auto-match docs → known artifacts; suggest edges; flag NEW) ──►
imported as "Needs review" ──► Review queue ──► Published ──► citizen graph
                                   ▲
                          Service editor (+ live MiniGraph preview) edits any stage

What's real in the prototype

  • The full flow, field parsing, confidence badges, dependency auto-matching & new-doc flagging
  • Lifecycle states + review queue + localStorage persistence
  • Live neighbourhood graph preview via the shared engine

What's mocked → needs backend

  • The scrape itself — browsers can't cross-origin fetch Irembo. Production = server-side scraper/fetcher job.
  • Persistence — localStorage → real DB + data API.
  • Admin edits → citizen graph — prototype didn't wire them back; needs the journey-assembly editor + publish pipeline.
  • Auth/roles — who can edit/approve/publish.

10Decisions

✓ locked = confirmed; ○ open = still to settle (don't block M0–M2).

D1 · Tech stack ✓ locked
Next.js + TypeScript. SSR/SEO so public journey pages are indexable & shareable. Engine + data as framework-agnostic packages.
D2 · First shippable ✓ locked
Citizen app only (M0–M2), no backend. Data ships as static validated JSON. Fastest path to the public wedge; admin + scraper follow.
D3 · Data source ✓ locked
Pure HTML scraping (beside). Server-side fetch + parse of public Irembo pages — no partnership required, matches the locked "beside, not integrated" stance. Built in Phase 4; design the parser to tolerate page changes (selectors-as-config, like the side-panel adapters).
D6 · Data accuracy ✓ locked
You arrange domain reviewers. We build the admin review queue + lifecycle; you bring people who know the real Irembo/agency processes to verify. Until then the citizen app carries a visible "estimates — verify with Irembo" note.
D4 · Persistence & hosting ✓ locked
Citizen app static-hosted (M2); host TBD (Vercel/Netlify vs gov infra), admin DB later. The static citizen build is host-agnostic, so we defer the host choice without blocking — revisit alongside the "free public good / grant-funded" model when the admin backend (M4) needs a home.
D5 · Admin auth & roles ✓ locked
Editor / Reviewer / Publisher roles gating the lifecycle. Editor drafts & imports → Reviewer approves out of the queue → Publisher pushes to the live citizen dataset. Wired in M4 (needs the backend); the M3 front-end is built role-aware from the start.
D7 · Kinyarwanda ✓ in scope
Bilingual is a committed goal, not a maybe. So we build i18n-ready from M0: every citizen-facing string (step name/short/desc, gotchas, "where", UI labels) carries an en + rw slot in the data model, even if rw starts empty. Content translation + native review is the Phase-5 push; the structure is laid now so it's not a retrofit.

11Known gaps the prototype leaves (from the chat)

⚠ Admin edits not wired to citizen graph

Journeys aren't editable yet — the "journey assembly editor" is a stub. An imported service can't yet be dropped into a citizen path. → M5.

⚠ Scrape is simulated

Returns realistic extractions for a small mock catalog. Real fetch is a server job. → M4.

⚠ Data is unverified

Modeled, not policy-checked. The lifecycle exists to fix this; the verification work itself is people, not code. → D6.

✓ Preview journeys now full

Birth, passport, driving, marriage are fully modeled with conditional branches (no longer stubs).
